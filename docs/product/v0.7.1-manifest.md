# v0.7.1 manifest — Dormancy signals (draft)

**Status:** In progress  
**Target release:** `v0.7.1`  
**Theme:** Explain-only **dormancy** context so users see “likely stale” vs “touched recently” before cleanup — no auto-delete or tier changes.

Parent: [v0.7.x-roadmap.md](v0.7.x-roadmap.md) · Follows [v0.7.0-manifest.md](v0.7.0-manifest.md).

---

## Problem

- `stale_days` and mtime already influence classification, but the UI does not surface **why** a path looks safe or review-worthy in dormancy terms.
- Users ask “why is this safe?” — dormancy copy should reduce anxiety without weakening quarantine-first safety.

## Candidate scope

| ID | Idea | Notes |
|----|------|--------|
| **D1** | **Dormancy label in candidate detail** | e.g. “Last modified N days ago” / “Within stale threshold” from `stale_days` + candidate mtime |
| **G1** | **Optional git last-commit age (opt-in)** | Setting-gated; only when `.git` ancestor exists; explain-only, never auto-delete |
| **U1** | **Sort / filter by dormancy** | Optional: “stale first” in candidate list (UI only) |

## Non-goals

- Auto-delete or lowering review tier based on dormancy heuristics  
- Mandatory git subprocess on every scan (opt-in only)  
- New `schema_version` unless scan report wire shape changes
